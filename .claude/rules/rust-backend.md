# Rust 侧规则

适用于 `src-tauri/` 下的所有代码。架构背景见 `docs/ARCHITECTURE.md`。

## 分层

- `commands/` 是**薄层**：只做参数校验、调用下层、把结果转成前端能用的形状。**不在 command 里写业务逻辑**——否则它会迅速膨胀成一个什么都干的文件，且无法脱离 Tauri 运行时单独测试。
- 业务逻辑放 `db/`、`ai/`、`scheduler/`，这些模块不依赖 Tauri 类型，可以直接写单元测试。

## 错误处理

- 对外（command 返回给前端）用统一的错误类型，携带一个稳定的错误码，前端据此决定提示文案。**不要把 Rust 的错误字符串直接甩给用户看。**
- 内部用 `Result` 传播，不用 `unwrap()` / `expect()`。启动期的不可恢复错误例外，但要写清 panic 信息。
- **错误信息里不得包含用户的待办标题和备注**（`CLAUDE.md` 安全红线）。只记类型和 id。

## 数据库

- 迁移脚本按序号命名，只增不改。**已发布的迁移永远不修改**，要改就加新的一条。
- 每个迁移必须在空库和有数据的库上都能正确执行。
- 删除一律软删除（写 `deleted_at`），不物理删除。所有查询默认过滤已删除记录。
- 任何写操作都要更新 `updated_at`。
- 表结构改动必须同步更新 `docs/DATA-MODEL.md`。

## 密钥

API Key 只走系统凭据管理器。**不写配置文件、不写数据库、不打日志。** 配置文件里只放 `base_url`、`model` 这类非敏感项。

## 外部请求

所有对外部服务的 HTTP 请求都在 Rust 侧发起。前端没有也不该有这个能力。

## 窗口与点击穿透

改 `window/` 之前先读 `docs/ARCHITECTURE.md` 的「点击穿透」一节。那里列了三个已知的坑（轮询频率与 CPU 的权衡、边界抖动、多显示器 DPI），改动前先确认你的方案没有重新踩进去。

轮询类逻辑要留意 CPU 占用——这是一个 24 小时常驻的程序，1% 的持续占用用户会在任务管理器里看到。
