## D1 · 客户端技术栈用 Tauri v2

**状态**：已定
**决策**：Rust 后端 + Web 前端（Tauri v2），Windows 优先，mac 后续适配。

**备选**：Electron / Python+PySide6 / C# WPF。

**理由**：桌宠是一个 24 小时挂在桌面的常驻程序，体积和内存直接决定用户会不会把它留下。

**后果**：
- 安装包约 8–15MB，常驻内存约 60–100MB。对比 Electron 的 90–150MB 安装包和 150–300MB 内存——后者对常驻桌宠是差评和卸载的主要来源。
- 托盘、窗口层级、点击穿透、开机自启这些系统集成都要写 Rust，团队里必须有人能读 Rust。
- 遇到冷门问题时，社区现成示例明显少于 Electron，排查时间会更长。
- 将来上 mac 主要是签名公证和窗口行为差异的适配，不需要重写。

**复议条件**：如果点击穿透（见 `ARCHITECTURE.md`）在 Tauri 上做了两周仍无法稳定，说明底层能力不足，届时重新评估。

## D2 · v1 只做内置形象，「用户上传图片转像素风」推迟到 v2

**状态**：已定

**理由**：形象转换是产品最大的传播点，但也是质量最不可控的一环。先把「桌宠 + 待办 + 语音改计划」这条主线跑通。

**后果**：
- v1 缺少最有记忆点的卖点，早期用户会问「不是说能传我家猫吗」。**对外文案必须提前管理预期**，不要在 v1 宣传页暗示这个能力已存在。
- 好处：v1 的形象质量完全可控，不会一上来就被「转出来的图很丑」拖住口碑。
- 约束：`PET-ASSETS.md` 里的 sprite 规格必须现在就定死，v2 的转换产物只要符合同一规格就能直接替换，不用重做渲染层。

**复议条件**：M2 结束后如果主线已经稳定且有富余人力，可以提前启动 v2 的转换管线预研。

## D3 · 语音与 LLM 全部走云端，用户自带 API Key（BYOK）

**状态**：已定

**备选**：产品方托管 key（自建中转后端）/ 本地 whisper.cpp。

**理由**：在「桌宠好不好玩」还没验证之前，不背服务器和调用成本。

**后果**：
- 我们不需要自建后端，没有调用成本，也不承担用户语音内容的存储责任——隐私上可以诚实地说「你的 key、你的账单、数据不经过我们」。
- **代价很实在**：普通用户根本不知道 API Key 是什么。这等于把语音和 AI 功能的首次体验门槛抬到了开发者水平，非技术用户会在设置页直接流失。
- 因此设置页的引导质量是产品成败项，不是打磨项：必须有分厂商的图文步骤，而不是一个空的输入框。
- 没有 key 时，产品必须仍然是一个完整可用的本地待办工具，不能整个卡死。

**复议条件**：如果 v1 的数据显示大量用户在设置页流失，说明 BYOK 是主要瓶颈，那时再评估托管方案（需同时接受服务器成本、限额、防滥用三项工作量）。

## D4 · 数据纯本地 SQLite，不做账号和多端同步

**状态**：已定

**后果**：
- 没有服务器、没有隐私合规负担、离线完全可用，v1 最省事。
- 换电脑数据不跟随，重装系统前用户得自己备份，也做不到「手机上看今天待办」。
- 因此 **v1 必须提供数据导出**（JSON），否则用户会觉得数据被锁死。这是 D4 的强制配套，不是可选功能。
- 表结构仍然保留 `updated_at` 和软删除字段（见 `DATA-MODEL.md`）：现在多花不到一天，将来接同步时不用做数据迁移、不用逼用户重建所有待办。

**复议条件**：出现明确的多端需求（用户主动要求 / 竞品对比劣势明显）时再评估。

## D5 · v1 内置形象先用开源或商用授权素材占位

**状态**：已定

**理由**：不让美术交付阻塞开发。

**后果**：
- 开发不被卡住，动画系统和交互可以立刻开始做。
- **形象没有辨识度，不能当品牌资产对外宣传**——这意味着 v1 不适合做以形象为主视觉的推广物料。
- **上线前必须逐条核对授权**：来源、许可证、是否允许商用、是否需要署名。核对表在 `PET-ASSETS.md`，漏一条就是法律风险。
- 大于 1MB 的美术素材入库需单独批准（见 `CLAUDE.md` 的 Git 规范）。

**复议条件**：确定要正式推广时，必须先完成一套自有形象替换占位素材。

## D6 · LLM 接入只实现 OpenAI 兼容协议

**状态**：已定

**决策**：只实现 OpenAI 兼容的 `chat/completions`。用户自填 `base_url` + `api_key` + `model`，界面提供几个常见厂商的快捷预设。

**后果**：
- 一套代码覆盖绝大多数国内外厂商，测试面小，维护成本低。
- Anthropic 原生协议、各家私有的结构化输出/缓存等特有能力都用不上。
- 与 D8 叠加后有额外约束，见下方「D6 × D8」。

**复议条件**：如果实测发现兼容协议下的工具调用质量不足以支撑「一句话改计划」，再考虑加一个原生 adapter（约 2–3 天工作量）。

## D7 · 宠物旁常驻一个可折叠迷你清单

**状态**：已定

**备选**：悬停出摘要卡片 + 点击开完整面板 / 只保留点击。

**理由**：产品的核心价值是「计划真的被看到」，藏在点击后面的清单和普通 to-do App 没有区别。

**后果**：
- 待办始终在视野里，对「帮我做计划」这个目标最直接。
- **常驻会占据桌面一块区域，桌宠的形态会往「悬浮窗」偏移**，反感的用户会直接卸载。因此折叠、贴边、透明度、拖动这几件事是核心体验，不是细节。
- 悬停不弹任何信息，只播放 `hover` 动画，避免鼠标扫过时误触。（「宠物看向鼠标」v1 不做）
- 点击宠物 = 折叠/展开清单。

**复议条件**：如果用户反馈集中在「太占地方」，评估改为默认折叠、只显示一个计数气泡。

## D8 · 语音走多模态 LLM，音频直接喂给模型

**状态**：**待验证**（阻塞于 M0 spike）

**备选**：独立 ASR 插件接口先转写再送 LLM。

**理由**：一次网络往返，延迟最低；且不会出现「ASR 转错一个字导致整条计划理解错」的级联错误。

**后果**：
- 交互延迟明显更低，链路更短，错误面更小。
- **可选模型大幅收窄**，见下方「D6 × D8」。
- 音频编码、体积上限、格式支持随厂商不同而不同，需要在 M0 实测。

**复议条件**：M0 spike 若发现主流厂商的 OpenAI 兼容端点普遍不支持音频输入，或延迟/失败率不可接受，则改用备选的独立 ASR 接口方案。

---

## D6 × D8 的叠加后果（重要）

两条决策叠加后，**可用模型 = OpenAI 兼容协议 且 支持 audio input**。DeepSeek、Kimi 这类纯文本模型，用户配了 key 也用不了语音。

强制的处理方式：

1. **文字自然语言输入是保底路径，不是可选项**。所有模型都支持文字，产品的 AI 能力不能只挂在语音上。
2. **设置页做能力探测**：保存配置后主动发一次极短音频试探，失败就当场提示「该模型不支持语音输入，你仍可以用文字改计划」。绝不能等用户对着麦克风说完一段话才报错——那是最糟的失败时机。
3. 快捷预设里要标注哪些厂商/模型支持语音。

## D9 · v1 功能边界

**状态**：已定

**做**：
- 待办带日期 / 截止时间；清单默认显示全部未完成，可勾选「只显示今日」
- 到点提醒（宠物冒泡 + 系统通知）
- 进度（二元勾选）
- 文字自然语言改计划（单轮，没有追问）
- 语音改计划（依赖 D8 的 M0 结论）
- 数据导出（D4 的强制配套）

**不做**（推迟理由见 `PRD.md` 的不做清单）：
- 重复任务、用户上传形象、账号与多端同步、开机自启、mac 版、唤醒词常听、百分比进度、AI 追问、悬停时看向鼠标

**后果**：
- 不做重复任务意味着「每天喝水」这类需求在 v1 无解，用户得每天手动加。这是已知取舍——重复规则叠加单次例外（这周跳过、改期只改这一次）的数据模型比看起来复杂得多，约多一周工作量。
- 进度只有对勾，「做了一半」这类状态在 v1 无法表达，用户只能写进备注。
- 没有追问：一句话说得含糊时，用户得整句重说，而不是只补一个细节。说错一个时间要重来一次，体验上比多轮对话笨，但换来的是 M3 不需要会话状态和对话 UI。
- 清单默认显示全部未完成，待办一多就会变长，和 D7「太占地方」的风险叠加。因此清单内部的条数折叠是必需功能，不是打磨项。
