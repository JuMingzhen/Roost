# AI 链路契约

> 前置阅读：[DECISIONS.md](./DECISIONS.md) 的 D3（BYOK）、D6（OpenAI 兼容协议）、D8（音频直喂模型）以及「D6 × D8 的叠加后果」。
> **改动本文的工具契约时，必须同步改 `src-tauri/src/ai/` 的实现；反之亦然。**

## 模型接入

只实现 **OpenAI 兼容的 `chat/completions`**。用户在设置页填 `base_url` + `api_key` + `model`，界面提供常见厂商的快捷预设。

### 能力探测（必做）

保存配置后，主动做两件事：

1. 发一次极短的文本请求，验证 key 和 base_url 有效；
2. 发一次极短的音频请求，验证该模型是否支持 audio input。

失败时**当场**提示「该模型不支持语音输入，你仍可以用文字改计划」，并在设置页标记语音不可用。

**绝不能等用户对着麦克风说完一段话再报错**——那是整个产品里最糟糕的失败时机。

### 两条输入路径

| 路径 | 可用性 | 说明 |
|---|---|---|
| 文字 | **所有模型可用，保底路径** | 用户敲一句话 |
| 音频 | 仅支持 audio input 的模型 | 录音后直接作为 message 内容送出（D8） |

产品的 AI 能力不能只挂在语音上。文字路径必须先做完、先做好。

## 工具契约

模型通过 function calling 返回操作。**所有工具都只描述意图，不直接执行。**

### `query_tasks`
读取待办。参数：时间范围、状态、关键词。唯一的只读工具。

### `create_task`
| 参数 | 类型 | 必填 |
|---|---|---|
| `title` | string | 是 |
| `note` | string | 否 |
| `due_at` | string (ISO 8601, 带时区) | 否 |
| `all_day` | boolean | 否，默认 false |

### `update_task`
| 参数 | 类型 | 必填 |
|---|---|---|
| `id` | string | 是 |
| `title` / `note` / `due_at` / `all_day` | 同上 | 否，只传要改的字段 |

### `set_done`
| 参数 | 类型 | 必填 |
|---|---|---|
| `id` | string | 是 |
| `done` | boolean | 是。`true` = 标记完成，`false` = 取消完成 |

进度只有二元对勾（D9），没有百分比。「完成」和「删除」是两种操作，模型不得用 `delete_task` 表达「做完了」。

### `delete_task`
| 参数 | 类型 | 必填 |
|---|---|---|
| `id` | string | 是 |

删除走软删除（见 `DATA-MODEL.md`），且**在预览里必须最醒目地标出**。

## 变更预览与确认（强制，不可绕过）

模型返回的写操作**一律不直接落库**。流程是：

1. 收集模型返回的所有工具调用；
2. 渲染成人话摘要，例如「新增 1 条：明天 15:00 复盘会；修改 1 条：周报截止时间改到周五」；
3. 删除操作单独高亮；
4. 用户点确认才写库；点取消则全部丢弃。

**理由**：BYOK 下我们无法保证用户配置的模型质量——便宜的小模型可能误解「把周报删掉那句话不算」这类表述。**模型误删用户攒了两周的计划，是不可挽回的失败**，而多一次点击的成本极低。这个权衡在任何情况下都不划算反过来。

即使将来模型质量提升，也只放宽到「纯新增操作可配置为免确认」，删除和批量修改永远需要确认。

## 相对时间解析

「明天」「下周三」「后天下午」必须解析成具体时间。

- 在 system prompt 里注入**当前本地时间和时区**，让模型自己算，返回带时区的 ISO 8601 字符串。不要让模型返回「明天」这种相对词再由代码解析——那等于把歧义留到了最后。
- 「今天」的边界用用户设定的一天起点（默认 04:00，见 `DATA-MODEL.md`）。**这个规则只能有一处实现**，「只显示今日」筛选和 AI 解析共用同一个函数，否则两边一定会不一致。
- 只有日期没有时刻的（「明天交报告」）标记 `all_day = true`。

## 上下文注入

每次请求带上：当前时间与时区、今日与近期的待办列表（含 id）。

**必须给 id**，否则模型无法引用已有待办来做修改和删除。

**待办列表要限量**——不能把用户全部历史待办塞进去，那会随使用时长线性推高每次调用的成本，而这笔钱是用户在付（BYOK）。默认只带今天前后各若干天的活跃待办，具体窗口在 M3 实测后定。

## 失败与降级

| 失败 | 用户看到什么 |
|---|---|
| 未配置模型 | 引导去设置页，同时说明「不配也能正常用本地待办」 |
| key 无效 / 鉴权失败 | 明确说是 key 的问题，给出去设置页的入口 |
| 网络失败 / 超时 | 可重试提示，**用户输入的原文必须保留**，不能让人重说一遍 |
| 模型不支持音频 | 在设置页就已提示；若仍走到这里，提示改用文字输入 |
| 返回无法解析 / 没有工具调用 | 把模型的文字回复原样显示给用户，不要假装成功。v1 没有追问，用户重新语音或文字输入 |
| 模型返回了不存在的 task id | 在预览阶段拦下，标为无效操作，不落库 |

原则：**任何 AI 相关的失败都不能影响本地待办的正常使用。** 没有 key、断网、模型挂掉，Roost 都还是一个完整可用的本地待办工具。

## Prompt 与回归

- system prompt 单独成文件，不散落在代码里。
- **prompt 改动必须附带回归用例**：一组固定的输入句子和期望的工具调用结果。没有回归用例的 prompt 改动等于盲改——同一句话在改动后可能变成完全不同的操作，而这直接作用在用户的真实计划上。
- 用例至少覆盖：新增带时间、新增不带时间、修改时间、标记完成 / 取消完成（不得误判为删除）、删除、一句话含多个操作、模糊表述（不产生工具调用、用文字说明没听懂，而不是瞎猜）。
